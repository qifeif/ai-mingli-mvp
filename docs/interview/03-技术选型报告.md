# 心易 AI 命理决策助手 · 技术选型报告

## 1. 技术目标

心易的技术目标不是让大模型“自由算命”，而是建立一个可控的 AI 产品架构：

1. 确定性事实由代码计算。
2. 专业知识由本地知识库检索。
3. 表达、解释、对话由大模型完成。
4. 高风险场景由安全规则和分类模型优先拦截。

因此技术选型围绕四个关键词：可控、可解释、低成本、可迁移。

## 2. 总体架构

```text
前端页面 public/
  app / diyun / renjiandao / hehun / chat
        |
        v
Node HTTP Server server.js
        |
        +-- 纯计算层 src/ziwei.js src/bazhai.js src/liuyao.js src/hehun.js
        +-- RAG 层 src/rag.js + knowledge/
        +-- LLM 适配层 src/llm.js src/stream.js
        +-- 安全层 src/pipeline.js prompts.js
        +-- 数据层 src/supabase.js + localStorage
```

## 3. 后端选型

| 选项 | 结论 | 理由 |
| --- | --- | --- |
| Node.js 内置 HTTP | 采用 | MVP 足够轻，零框架，部署简单 |
| Express / Koa | 暂不采用 | 当前路由规模可控，引入框架收益有限 |
| Next.js | 暂不采用 | 当前重点是验证 AI 链路，不需要 SSR |
| Python FastAPI | 暂不采用 | 命理计算与前端栈已在 Node 侧沉淀 |

采用 Node 内置 HTTP 的好处：

- 依赖少，调试直接。
- 前后端静态资源和 API 同源部署。
- 适合 POC 快速迭代。

未来当 API 增多、权限复杂、运营后台上线时，可迁移到 Express/Fastify 或独立 BFF。

## 4. 前端选型

| 选项 | 结论 | 理由 |
| --- | --- | --- |
| 原生 HTML/CSS/JS | 采用 | 交互可控，启动成本低，适合作品集展示 |
| React/Vue | 暂不采用 | 当前页面逻辑虽多，但尚未达到必须组件化的复杂度 |
| Tailwind | 暂不采用 | 已有 `theme.css` 设计系统，避免风格分裂 |

前端设计重点：

- 多页面工具型体验，而非营销 landing 为主。
- 命盘、罗盘、卦象等结构化可视化。
- SSE 流式渲染，降低 AI 等待焦虑。
- 中英文 i18n 字典和 EN 模式约束。

## 5. 命理计算选型

### 5.1 紫微斗数

采用 `iztro` 作为底层安星库。

原因：

- 已支持紫微斗数核心排盘。
- 可以输出十二宫、主星、辅星、四化、大限流年。
- 避免从零手写复杂安星规则。

项目自实现部分：

- 真太阳时校正。
- 出生地经度解析。
- 三方四正结构化。
- 格局识别。
- 前端命盘九宫格映射。

### 5.2 八宅风水

采用自实现规则引擎。

原因：

- 八宅本命卦与方位吉凶规则清晰。
- 计算成本低，不需要模型参与。
- 更适合输出稳定结构给前端展示。

### 5.3 六爻

采用自实现摇卦与卦表。

原因：

- 摇卦过程可控。
- 本卦、动爻、变卦结构容易序列化。
- AI 只负责解释，不负责随机起卦。

### 5.4 合参

采用自实现八字对照规则。

覆盖：

- 日主天干互动。
- 十神互看。
- 地支六合、六冲、三合、相刑、相害。
- 五行互补。
- 婚恋/合伙双模式总结。

## 6. 模型接入选型

| 模型层 | 任务 | 推荐配置 |
| --- | --- | --- |
| 主解读模型 | 长文本解释、对话、综合判断 | `LLM_TEXT_MODEL`，如 qwen-plus / Claude Sonnet |
| 分类模型 | 危机检测、场景分类 | `LLM_CLASSIFY_MODEL`，如 qwen-turbo / Claude Haiku |
| 视觉模型 | 户型图点评 | `LLM_VISION_MODEL`，如 qwen-vl-max |

项目采用双 provider 适配：

- Anthropic 原生 SDK。
- OpenAI-compatible Chat Completions。

这样可以在海外模型和国内模型之间切换，避免供应商锁定。

## 7. RAG 方案

采用本地文件知识库 `knowledge/`，由 `src/rag.js` 自动读取 Markdown、TXT、JSON。

能力：

- 自动按目录推断领域：bazi、ziwei、liuyao、fengshui、hehun、renjiandao。
- Markdown section 切块。
- 中文 n-gram 与关键词召回。
- 输出 `<knowledge>` 注入 prompt。

暂不采用向量数据库的原因：

- POC 知识规模较小，本地关键词检索足够。
- 免去 embedding 成本与部署复杂度。
- 更容易在面试中解释和复现。

未来升级：

- 引入 embedding rerank。
- 增加 chunk 质量标注。
- 对不同领域建立专属检索策略。

## 8. 流式输出选型

采用 SSE。

原因：

- 浏览器原生支持。
- 服务端实现轻量。
- 适合 AI 文本逐字输出。
- 对天命页可实现“两段式”：命盘骨架先出，AI 深化后出。

WebSocket 暂不采用：

- 当前不需要双向实时协作。
- SSE 更适合单向流式文本。

## 9. 数据存储选型

| 场景 | 方案 | 理由 |
| --- | --- | --- |
| 未登录体验 | localStorage | 降低试用门槛 |
| 登录认证 | Supabase Auth | 快速获得邮箱登录能力 |
| 用户数据 | Supabase `user_data` | 支持命例、对话、生辰档案统一存储 |
| 服务端代理 | Node API | 避免 service role key 暴露前端 |

数据策略：

- 未登录也可完整体验。
- 登录后自动迁移本地数据。
- 用户数据按 key-value 保存，适合 MVP 快速扩展。

## 10. 安全方案

安全策略分三层：

1. 输入前置检测：用户问题先进入危机分类。
2. 高风险短路：命中 risk 时不排盘、不解释命理。
3. Prompt 红线：主解读禁止确定性预测和高风险建议。

危机检测失败时采取从严策略：当作 risk 处理，避免漏拦。

## 11. 替代方案评估

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| 全部交给 LLM 算命 | 开发快 | 幻觉高、不可解释 | 不采用 |
| 纯规则无 LLM | 稳定、便宜 | 体验僵硬、无法追问 | 不采用 |
| 计算 + LLM | 准确与体验平衡 | 需要维护契约 | 采用 |
| 向量数据库 RAG | 召回能力强 | 部署和成本更高 | 后续升级 |
| 单一模型供应商 | 接入简单 | 成本与稳定性受限 | 不采用 |

## 12. 技术风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 模型输出不稳定 | 解读质量波动 | 评测集 + prompt 约束 + Bad case 回归 |
| RAG 召回不准 | 引用知识偏差 | 分领域检索 + 调试接口 |
| 前端单文件膨胀 | 维护困难 | 后续组件化拆分 |
| 用户隐私风险 | 信任受损 | API Key 服务端化，用户数据最小化 |
| 视觉模型成本高 | 商业化压力 | 图片压缩 + 非必需路径 |

## 13. 结论

本项目的技术选型适合 POC 到初版上线阶段。核心优势是把命理事实计算、知识检索与模型表达分离，避免让大模型承担它不擅长的确定性计算，同时利用大模型擅长的自然语言解释、多轮承接与个性化表达。
